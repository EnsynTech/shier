# 识饵管理端前端技术选型决策


| 项    | 内容                                     |
| ---- | -------------------------------------- |
| 状态   | **已批准**                                |
| 日期   | 2026-09-19（方案 B 确认：2026-09-21）         |
| 范围   | 管理端 UI（Admin）。钓鱼落地页、邮件 HTML、场景包素材不在范围内 |
| 参考 | 产品 Demo：`docs/ui-redesign-demo.html`；竞品调研：`docs/ui-competitive-research.md` |
| 选定方案 | **方案 B：渐进增强**                          |


---

## 1. 决策结论

管理端采用 **渐进增强**：

- **壳与路由**：继续由 Go 模板负责（登录、会话、CSRF、i18n 注入、页面骨架）。  
- **热点交互**：在「发起演练向导」「工作台」「结果分析」等页面，用**单一**轻量运行时做局部增强（小岛挂载到指定 DOM）。  
- **视觉**：更轻的定制设计（CSS 变量设计令牌），不以 Ant Design 类高密度企业套件为主。  
- **浏览器**：现代浏览器即可（近两年版本的 Chrome / Edge / Firefox / Safari），不做旧内网浏览器降级。  
- **部署**：运行时仍是 Go 单进程；若小岛需打包，仅在 CI 产出静态文件，镜像内不跑 Node。

**不采用**：管理端整体 SPA 重写（原方案 C）、Next.js / Nuxt 等 Node 全栈运行时、在钓鱼页引入管理端同一套增强栈。

## 2. 现状基线


| 层   | 现状                                        |
| --- | ----------------------------------------- |
| 页面  | Go 模板（`templates/`）                       |
| 脚本  | 页面级 jQuery（`static/js/src/app/`），gulp 压缩  |
| 样式  | Bootstrap 3 系 + 多套第三方 CSS 拼装              |
| 国际化 | 服务端注入 locale；Accept-Language 自动选择，无手动语言开关 |
| API | 已有 JSON API，前端经会话 / API Key 调用            |


产品能力（场景包、多步骤、多通道、部门标签等）已多于当前 UI 表达；瓶颈在任务流与信息架构，不在「有没有完整 SPA」。

---



## 3. 方案 B 怎么落地



### 3.1 技术约束（择一，勿叠加）

热点页增强栈**只选一种**，禁止 Alpine + React + Vue 混用：


| 候选                        | 适用              |
| ------------------------- | --------------- |
| Alpine.js / petite-vue    | 状态中等、希望改动面最小    |
| Vite 打包的单个 React 或 Vue 小岛 | 向导 / 工作台状态明显复杂时 |


React 与 Vue 在立项小岛工程时按团队技能二选一；未立项前不绑死。

### 3.2 目录与边界（建议）

- 壳、导航、CRUD 列表页：继续 Go 模板 + 现有 JS，先做信息架构与文案改造。  
- 小岛源码（若启用打包）：独立目录（例如 `web/islands/`），构建产物进 `static/`，由模板按需引入。  
- 文案：继续单一 `i18n/locales/*.json`；小岛内禁止散落硬编码中英文。  
- 钓鱼相关 HTML：保持朴素，不引入小岛框架。



### 3.3 视觉与 CSS

尽早建立识饵设计令牌（主色、状态色、间距、字体层级），在现有页面上用 CSS 变量逐步覆盖 Bootstrap / Flat UI 观感。

- 对齐 Demo：留白更多、层级更轻、品牌绿为主。  
- 允许使用现代 CSS（变量、Grid、较新选择器）。  
- 令牌一致性优先于是否引入 Tailwind；若引入，仅作工具类，不替代设计令牌。



### 3.4 优先增强的页面（与产品阶段对齐）

```text
P0  导航重组 / 场景入口 / 文案业务化     → 模板 + CSS 令牌（可不挂小岛）
P1  发起演练向导                         → 首选小岛增强点
P2  工作台 + 部门风险 + 高风险名单         → 第二批小岛
P3  管理层简报 / 培训闭环                → 在 B 内扩展；勿借机全面 SPA
```

## 4. 为何不是其他方案（摘要）


| 方案              | 结论      | 原因                           |
| --------------- | ------- | ---------------------------- |
| A 纯模板+jQuery 到底 | 不作为终态   | 向导与工作台状态会继续堆进巨型 JS，组件难复用     |
| C 管理端整体 SPA     | 否决（本阶段） | 成本高、upstream 合并面大，且不自动改善信息架构 |
| D Next/Nuxt 全栈  | 否决      | 双运行时，与 Go 单进程 / 内网交付冲突       |


若未来小岛数量过多、共享组件成本高于维护双轨，再单独立项评估是否升到整体 SPA；**当前不设默认 SPA 栈，也不预写迁移切片清单。**

---



## 5. 风险与非目标


| 风险         | 缓解                          |
| ---------- | --------------------------- |
| 双轨永久化、纪律松懈 | 明确「哪些页准用小岛」；新增热点需评审，禁止无约定扩散 |
| 多种增强库叠加    | 全文只允许一种增强运行时                |
| i18n 分裂    | 单一文案源；小岛构建时同步或运行时注入         |
| 构建进运行时     | 仅 CI 产出静态资源                 |
| 为换栈而换栈     | 产品路径与 Demo 验收优先于技术新鲜度       |


**非目标：** 用前端技术提升发信性能、对抗检测，或替代场景包内容质量。
